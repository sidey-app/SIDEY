# SIDEY 제품 기획서

- 문서 버전: 0.1
- 최종 갱신: 2026-08-31
- 상태: 초기 기획
- 현재 대상 플랫폼: macOS 26 이상 Apple Silicon
- 후속 플랫폼: Windows 별도 클라이언트

## 1. 제품 정의

`SIDEY`는 최대 5명의 가까운 친구가 3D 캐릭터 형태로 사용자의 컴퓨터 화면 위에 머물며, 친구의 온라인·자리 비움·타이핑 상태와 메시지를 실시간으로 보여주는 데스크톱 프로그램이다.

일반적인 메신저처럼 채팅방 목록을 계속 확인하는 방식이 아니라 친구의 존재를 화면에서 자연스럽게 느끼는 **Ambient Messenger**를 지향한다.

제품명은 `SIDEY`다. 이전 가칭인 `같이온` 또는 `같이ON`은 사용하지 않는다. 공식 슬로건은 아직 정하지 않았다. 출시 전 상표와 도메인을 확인해야 한다.

### 핵심 가치

- 친구가 지금 컴퓨터 앞에 있는지 자연스럽게 알 수 있다.
- 별도 메신저 창을 열지 않고 짧은 메시지를 주고받는다.
- 실제 친구가 귀여운 캐릭터로 화면 곁에 머무는 느낌을 준다.

각 캐릭터는 실제 친구 한 명을 나타낸다. AI 캐릭터나 가상 반려동물 제품으로 만들지 않는다.

## 2. MVP 범위

첫 버전은 의도적으로 작게 만든다.

### 2.1 그룹

- 그룹당 최대 5명
- 방 생성자가 초대 코드를 만들고 친구가 코드를 입력해 참여
- 참여 후에는 코드를 반복해서 입력하지 않음
- 최대 인원은 서버에서 강제로 제한
- 사용자당 최대 5개 그룹에 참여 가능
- 오버레이에는 한 번에 활성 그룹 하나만 표시
- 그룹 이름은 생성 시 1~20자로 입력하고 방장이 변경 가능

### 2.2 캐릭터

- 기본 캐릭터 5종
- 캐릭터는 개인 프로필에서 하나 선택하며 모든 그룹에 동일하게 적용
- 내부 사용자 식별은 UUID로 처리하고 캐릭터와 닉네임은 표시용으로 사용
- 초기 버전에는 캐릭터 커스터마이징 없음
- 같은 방에서도 캐릭터 중복 선택을 허용
- 색상, 머리, 의상, 소품 변경은 후속 기능

현재 macOS vertical slice는 `minty_pup_station_v3_animated.glb`을 사용한다. 크림색 Minty Pup과 파란 후드, 밝은 쿨 실버 노트북, 살구빛 크림 우드 책상·의자가 사용자 승인된 애니메이션풍 외형이다. 털 영역 roughness 중앙값은 약 0.79로 올려 머리의 플라스틱 광점을 줄이되 눈·코의 광택은 유지하며, 책상 가로폭은 원본 대비 68.64%다. 캐릭터·책상·의자·노트북 베이스·노트북 덮개는 독립 오브젝트이며, 캐릭터는 19-bone skeleton과 세 상태 모션을 가진다. macOS 번들에는 이 GLB에서 변환하고 512 텍스처로 제한한 모션별 USDZ를 넣는다. SceneKit 조명은 따뜻한 키라이트와 부드러운 쿨 필라이트를 사용하며 실시간 그림자는 사용하지 않는다.

### 2.3 상태

백엔드의 논리 상태는 다음 네 가지다.

- 온라인
- 타이핑 중
- 자리 비움
- 오프라인

에셋을 단순하게 유지하기 위해 자리 비움과 오프라인은 같은 `조는 모습`을 공유할 수 있다.

| 실제 상태 | 캐릭터 표현 |
| --- | --- |
| 컴퓨터 사용 중 | 눈을 뜬 기본 idle |
| SIDEY 채팅 입력 중 | 키보드 타이핑 |
| 일정 시간 시스템 입력 없음 | 조는 모습 |
| 화면 잠금·절전 | 조는 모습 |
| 앱 종료·연결 끊김 | 조는 모습 |
| 다시 활동 시작 | 온라인 idle로 직접 전환 |

백엔드에서는 `idle`과 `offline`을 구분하되 초기 캐릭터 표현은 같게 가져간다.

### 2.4 채팅

MVP에서는 그룹 채팅 하나만 제공한다.

- 사용자가 메시지를 입력하는 동안 다른 친구 화면에서 해당 캐릭터가 타이핑함
- 전송 후 해당 캐릭터 위에 말풍선 표시
- 말풍선은 일정 시간이 지나면 자동으로 사라짐
- 최근 기록 패널에서 메시지를 다시 확인 가능하며 가장 최근 메시지를 맨 위에 표시
- 1:1 DM은 후속 버전
- 이미지, 파일, 음성, 영상 통화는 MVP에서 제외
- 말풍선은 텍스트 가독성과 반응형 배치를 위해 3D 모델이 아닌 2D UI로 구현

## 3. 기본 사용자 흐름

### 3.1 최초 실행

```text
프로그램 설치
→ 첫 네이티브 실행에만 2초 브랜드 랜딩
→ 기존 사용자는 저장 세션 복원 결과가 확정될 때까지 랜딩에서 대기
→ 1단계: 닉네임과 현재 제공되는 캐릭터 선택
→ 2단계: 방 만들기 또는 코드로 입장
→ 온보딩 창 종료 후 설정의 그룹 페이지에서 현재 그룹 확인
→ 오버레이 위치 설정
→ SIDEY 시작
```

온보딩은 논리 크기 960×720의 일반 창에서 진행하고 OS 디스플레이 배율을 적용한다. 1단계를 통과해야 그룹 연결 단계로 이동하며, 뒤로 가면 입력한 프로필 초안을 유지한다. 2단계에서는 `새 그룹 만들기`와 `초대 코드로 참여` 탭 중 하나의 폼만 표시한다. 그룹 생성 또는 참여가 성공하면 온보딩 창을 먼저 닫고 설정의 `그룹` 페이지를 열어 현재 그룹과 초대 정보를 바로 보여준다. 완료된 온보딩은 프로필 1단계로 다시 열리지 않는다.

기존 온보딩 완료 상태가 있는 사용자는 저장된 Supabase 세션 또는 기존 refresh token이 복원된 뒤에만 오버레이를 연다. 복구 자료가 없거나 refresh가 실패하면 새 익명 계정을 자동 생성하지 않고 설정창에 복구 오류를 표시한다.

### 3.2 방 만들기

```text
방 만들기
→ 안전한 랜덤 초대 코드 발급
→ 친구에게 코드 전달
→ 최대 4명 추가 참여
```

초대 코드는 추측하기 쉬운 4자리 숫자 대신 약 8자리의 영문·숫자 조합을 사용한다.

```text
7KM4-NP2Q
```

초대 코드는 계정 비밀번호가 아니라 방에 최초 가입하기 위한 수단이다. 유출되면 방장이 폐기하고 새로 발급할 수 있어야 한다.
초대 코드는 방장이 재발급하기 전까지 유효하고, 재발급 즉시 기존 코드는 무효화한다. 데이터베이스에는 원문이 아니라 해시만 저장한다.

### 3.3 메시지 전송

```text
내 캐릭터 아래의 상시 입력창에 입력
→ 입력하는 동안 내 캐릭터가 타이핑
→ 다른 친구 화면에서도 내 캐릭터가 타이핑
→ Enter로 전송(Shift+Enter는 줄바꿈)
→ 클라이언트가 UUID를 발급하고 내 캐릭터 위에 말풍선을 즉시 표시
→ 같은 UUID로 Postgres 저장
→ 모든 방 멤버에게 같은 메시지 전달
```

macOS 네이티브 텍스트 입력의 표준 IME 조합 처리를 사용한다. `Enter`는 전송, `Shift+Enter`는 줄바꿈이며 입력은 최대 200자·3줄이다. 제한을 넘으면 마지막 정상 draft로 복구하고 전송 후에는 입력창을 닫지 않고 내용만 비운다.

내가 보낸 메시지는 서버 왕복을 기다리지 않고 로컬 기록과 말풍선에 낙관적으로 즉시 반영한다. Postgres 저장과 Realtime 재수신은 동일한 클라이언트 UUID로 중복 제거하며, 저장 실패 시 낙관적 기록을 제거하고 전송 원문을 입력창에 복구한 뒤 실패 상태를 표시한다. 다른 멤버에게 전달되는 메시지와 재접속 후 복원되는 기록의 원본은 계속 Postgres다.

## 4. 오버레이 UI

### 4.1 기본 형태

- 투명한 배경
- 창 테두리 없음
- 일반 프로그램보다 항상 위
- 최대 5명의 상반신 캐릭터를 가로 또는 완만한 곡선으로 배치
- 캐릭터 아래에 상태 dot, 닉네임, `나` 표시가 들어간 검정 반투명 pill 배치
- 자물쇠와 메시지 입력은 별도 Liquid Glass 상호작용 패널에 항상 표시
- 이동·크기 조절·최근 기록·설정은 잠금 해제 시 같은 패널에 확장 표시
- 하단 상호작용 패널은 잠금 400×56, 편집 580×56 논리 포인트의 컴팩트 크기를 사용
- 메시지 수신 시 캐릭터 위에 말풍선 표시
- 말풍선은 흰색 바탕과 진한 글자로 표시하고, 기존 가로 폭을 유지한 채 내용에 따라 최대 10줄까지 세로로 확장
- 캐릭터 크기를 조절하면 스케일 적용 후 머리 상단의 화면 좌표를 다시 계산해 말풍선도 함께 이동하며, 머리와의 간격은 일정하게 유지
- 말풍선 하나만 보이면 해당 캐릭터 머리에 가장 가까운 lane에 배치하고, 인접 말풍선이 동시에 보일 때만 상단 lane으로 올리며 화면 좌우에서 잘리지 않게 보정
- 투명 창은 200% 영역으로 고정하고 캐릭터와 닉네임만 150~200%로 조절하며 입력창·말풍선·기록·편집 tray는 160% 크기로 고정
- 방 이름은 오버레이에 표시하지 않음

```text
       “저녁 뭐 먹을래?”
               ╭────────────╮
               │            │
        [A]     [B]     [C]     [D]     [E]
       민수    지현     나      준호     수빈
```

실제 화면에는 이모지 대신 3D 상반신 캐릭터가 들어간다.

### 4.2 위치 이동과 복원

MVP에서는 캐릭터를 하나씩 움직이지 않고 전체 캐릭터 그룹을 하나의 오버레이 묶음으로 이동한다.

- 편집 모드에서 이동 아이콘을 드래그할 때만 이동
- 위치와 모니터 식별 정보를 로컬에 저장
- 다음 실행 시 같은 위치 복원
- 화면 밖으로 완전히 사라지지 않도록 위치 보정
- 멀티 모니터 지원
- 저장한 모니터가 제거되면 주 모니터로 자동 복귀

### 4.3 클릭 통과

항상 위에 있는 오버레이가 다른 프로그램의 클릭을 방해하지 않도록 두 모드를 제공한다.

#### 잠금 모드

- 캐릭터·말풍선·빈 배경을 포함한 전체 아바타 패널의 마우스 클릭이 뒤 프로그램으로 통과
- 별도의 작은 상호작용 패널에는 자물쇠와 채팅 입력을 항상 표시
- 이동·크기 조절·최근 기록·설정 조작은 숨김
- 기본 모드로 사용

#### 편집 모드

- 잠금 상태의 Liquid Glass 패널을 확장해 이동, 크기 조절, 최근 기록, 설정 조작을 추가 표시
- 이동 아이콘을 드래그할 때만 아바타 오버레이 프레임 이동 가능
- 잠금 아이콘이나 메뉴바 명령으로 잠금 모드에 복귀

아바타 패널은 항상 `ignoresMouseEvents`로 클릭을 통과시킨다. 자물쇠와 채팅 입력이 있는 작은 패널만 입력을 받고, 나머지 투명 영역은 뒤 애플리케이션의 클릭을 가로채지 않는다.

메뉴바 명령으로 두 모드를 전환한다. 잠금은 오버레이 위치를 보호하고 평상시 클릭 통과를 보장하는 상태다.

### 4.4 메뉴바·시스템 트레이

macOS 메뉴바와 Windows 시스템 트레이에서 다음 기능을 제공한다.

- 오버레이 보이기/숨기기
- 활성 그룹 선택과 그룹별 읽지 않은 수 확인
- 메시지 작성
- 상호작용 잠금/해제
- 조용히 모드
- 위치 초기화
- 그룹 설정
- 로그인 시 자동 실행
- 프로그램 종료

### 4.5 조용히 모드

화면 공유나 집중 작업 중 메시지가 갑자기 노출되지 않도록 한다.

- 캐릭터는 유지
- 타이핑 동작은 선택적으로 숨김
- 말풍선 자동 표시 안 함
- 활성 그룹의 미확인 메시지는 아바타의 작은 점으로, 모든 그룹의 미확인 수는 메뉴바 그룹 목록에 표시
- 소리 없음

친구별 음소거는 후속 기능으로 둔다.

### 4.6 설정 창

설정은 오버레이와 분리된 일반 데스크톱 창으로 제공한다.

- 논리 기본 크기 1000×760, 최소 크기 860×640에 OS 디스플레이 배율 적용
- 좌측 메뉴에서 `내 프로필`, `그룹`, `앱 설정`을 전환
- 본문·보조문구는 SwiftUI 의미론적 시스템 폰트를 사용하고 입력·버튼은 macOS 기본 컨트롤 크기와 접근성 설정을 따르며 수동 픽셀 배율을 적용하지 않음
- 본문 섹션은 시스템 `GroupBox`로 구분하고 Liquid Glass는 사이드바·오버레이 조작면·상위 피드백처럼 계층상 필요한 곳에만 사용
- 프로필에서는 닉네임과 캐릭터, 그룹에서는 활성 그룹·그룹 추가·초대·멤버 관리와 각 그룹의 초대 코드 복사, 앱 설정에서는 로그인 시 자동 실행을 관리
- 그룹별 초대 코드 복사는 이 기기 Keychain에 원문이 있을 때만 동작한다. 서버에는 해시만 저장하므로 원문이 없는 기존 그룹은 복구할 수 없다는 오류를 표시한다.
- 작은 창에서는 좌측 메뉴를 고정하고 현재 내용 영역만 세로 스크롤
- 처리 결과는 현재 페이지 상단의 인라인 성공·오류 배너로 표시

## 5. 캐릭터 상태 모델

서버는 애니메이션을 직접 재생시키지 않는다. 서버가 전달한 상태와 이벤트를 각 클라이언트가 해석해 로컬에서 애니메이션을 재생한다.

```text
online_idle ←→ typing
     ↕
offline_sleep
```

별도 전환 클립은 사용하지 않는다. 세 모션을 직접 전환하며 한 프레임 포즈 튐을 막는 최대 0.15초 블렌드만 허용한다.

### 5.1 애니메이션 우선순위

상태가 충돌하면 다음 순서를 적용한다.

```text
연결 종료/자리 비움
> 타이핑
> 메시지 반응
> 온라인 idle
```

예를 들어 타이핑 중 연결이 끊기면 타이핑을 즉시 중단하고 `offline_sleep`으로 전환한다.

### 5.2 상태 전환 규칙

- 앱 연결 성공 → 온라인 후보
- 최근 OS 입력이 있고 화면이 잠기지 않음 → 온라인
- 일정 시간 키보드·마우스 입력 없음 → 자리 비움
- 화면 잠금 또는 절전 → 자리 비움
- 프로그램 정상 종료 → 오프라인
- 갑작스러운 네트워크 종료 → Presence timeout 후 오프라인
- SIDEY 채팅 입력창에서 글자 입력 → 타이핑
- 입력이 일정 시간 멈춤 → 타이핑 자동 종료
- 메시지 전송 → 타이핑 종료 후 말풍선 표시

타이핑 상태는 SIDEY 입력창에서 입력할 때만 감지한다. 다른 프로그램에서 입력한 키의 내용이나 이벤트를 수집하지 않는다.

## 6. 온라인 상태의 정의

초기 목적은 앱 실행 여부가 아니라 친구가 실제로 컴퓨터를 사용하고 있는지를 보여주는 것이다.

### 온라인

- SIDEY 실행 중
- Supabase 실시간 연결 정상
- 해당 사용자가 현재 보고 있는 활성 그룹
- 화면 잠금 상태 아님
- 최근 키보드 또는 마우스 입력 존재

### 자리 비움

- 프로그램과 서버 연결은 유지
- 일정 시간 동안 시스템 입력 없음
- 또는 화면이 잠김

### 오프라인

- 프로그램 종료
- 컴퓨터 절전 또는 종료
- 네트워크 연결 끊김
- Supabase Presence에서 해당 사용자가 사라짐
- SIDEY에는 연결되어 있지만 해당 방이 현재 활성 그룹이 아님

MVP의 자리 비움 기본 기준은 5분이다. 갑작스러운 종료나 네트워크 단절은 서버의 heartbeat timeout 이후에 감지되므로 오프라인 전환이 즉시 나타나지 않을 수 있다.
클라이언트는 메시지와 읽지 않은 수를 받기 위해 참여 중인 모든 방의 Realtime 채널을 유지하되, Presence에는 활성 그룹에서만 `online` 또는 `away`를 게시하고 나머지 그룹에는 `offline`을 게시한다. 그룹을 전환하면 이전 그룹과 새 그룹의 상태를 즉시 함께 갱신하며, 현재 화면의 내 캐릭터는 서버 왕복을 기다리지 않고 로컬 활동 상태를 먼저 반영한다.

Realtime 연결 완료는 참여 중인 모든 방 채널의 구독 상태를 합산해 판단한다. 연결이 끊기면 저장 대상이 아닌 타이핑 상태는 즉시 제거하고 새 Broadcast를 받은 뒤에만 다시 표시한다. Presence가 상태 교체를 같은 사용자의 `leave(old)+join(new)` delta로 전달하면 새 join을 우선해 `away` 같은 최신 상태가 `offline`으로 덮이지 않게 한다.

## 7. 기술 구성

macOS 제품 품질과 장시간 성능을 우선하기 위해 macOS 클라이언트는 네이티브 Swift로 개발한다. Windows는 이 코드베이스의 현재 vertical slice와 결합하지 않고 별도 클라이언트로 후속 개발한다.

```text
                   ┌────────────────────┐
                   │      Supabase      │
                   │                    │
                   │ Auth / Postgres    │
                   │ Presence/Broadcast │
                   └─────────┬──────────┘
                             │ HTTPS / WebSocket
                      ┌──────▼───────────┐
                      │ macOS arm64 .app │
                      │ SwiftUI / AppKit │
                      │ SceneKit + USDZ  │
                      └──────────────────┘
```

### 7.1 macOS 클라이언트

SwiftUI는 랜딩·온보딩·설정·오버레이 조작 UI를 담당하고, AppKit은 창 생명주기와 macOS 시스템 기능, SceneKit은 USDZ 3D 캐릭터 재생을 담당한다. RealityKit은 번들 USDZ가 최신 Apple 로더에서도 열리는지 자동 테스트하는 호환성 경계로 사용한다.

- 랜딩·설정 창과 오버레이 창은 독립된 window controller가 소유한다.
- 설정 창은 `.normal` 레벨의 일반 창이며 다른 앱 뒤로 이동할 수 있다.
- 아바타·말풍선 패널만 `.floating` 레벨과 모든 Space 정책을 사용한다.
- 아바타 패널은 클릭을 통과시키고 입력창·편집 tray·기록은 별도의 작은 대화형 패널로 제공한다.
- 설정 창을 닫거나 숨겨도 오버레이는 유지되며, 아바타 이동은 오버레이 패널 묶음만 움직인다.
- Supabase Swift SDK 2.55.1을 Xcode 프로젝트와 `Package.resolved` 양쪽에 정확히 고정해 익명 Auth, Postgres, Presence, Broadcast를 사용한다.
- 네트워크는 actor 기반 서비스가 담당하고 USDZ 파싱은 백그라운드 task에서 처리하며 window/UI 상태는 `@MainActor`에서만 갱신한다.

### 7.2 macOS 시스템 기능

- 사용자 입력 idle 시간 확인
- 화면 잠금·해제 감지
- 전체 Space 표시 정책
- 메뉴바 아이콘
- 로그인 시 자동 실행
- 전역 단축키
- 앱 서명 및 공증
- Keychain 기반 기존 익명 세션·초대 코드 이전
- 기존 활성 방과 오버레이 위치·배율·잠금·표시 설정 이전

#### 7.2.1 macOS alpha 배포

- 첫 공개 테스트 빌드는 macOS 26 이상 Apple Silicon을 지원하는 arm64 `.app`을 ZIP으로 제공한다.
- 유료 Apple Developer Program 가입 전에는 Xcode Release 결과를 ad-hoc 서명하고 Apple 공증은 하지 않는다.
- GitHub Release를 사전 릴리스로 표시하고 README와 릴리스 노트에 Gatekeeper 수동 허용 절차와 위험을 명확히 적는다.
- ZIP과 SHA-256 체크섬 파일을 함께 제공하며 설치 파일은 Git 저장소에 커밋하지 않는다.
- 이 alpha 방식은 정식 배포를 대체하지 않는다. 정식 macOS 배포 전에는 Developer ID 서명과 Apple 공증을 완료한다.

### 7.3 Windows 후속 개발

Windows 클라이언트의 언어·렌더러·최소 버전·배포 방식은 별도 제품 결정으로 다룬다. macOS 네이티브 vertical slice 완료 전에는 Windows 구현을 진행하지 않는다.

### 7.4 오버레이 한계

일반 앱과 borderless fullscreen 위에는 표시할 수 있지만 다음 영역에서는 표시를 보장하지 않는다.

- Windows UAC 보안 화면
- macOS 로그인·잠금 화면
- 일부 DRM·보안 프로그램
- 일부 exclusive fullscreen 게임
- OS 권한이 더 높은 관리자 프로그램
- 화면 캡처 차단 정책이 적용된 앱

제품 설명에서 “모든 상황에서 무조건 최상단”이라고 홍보하지 않는다.

## 8. Supabase 구성

### 8.1 최소 데이터 모델

#### `profiles`

```text
id
nickname           2~12자
character_id       기본 minty_pup
created_at
updated_at
```

#### `rooms`

```text
id
name
owner_id
invite_code_hash
invite_code_hint
invite_version
created_at
```

#### `room_members`

```text
room_id
user_id
joined_at
```

캐릭터 목록과 에셋 경로는 클라이언트의 로컬 `CharacterCatalog`가 관리한다. 캐릭터 선택은 `profiles.character_id`에만 저장하며 중복 제약을 만들지 않는다.

#### `messages`

```text
id
room_id
sender_id
body
created_at
```

메시지 ID는 클라이언트가 만든 UUID를 사용해 재전송 중복을 막는다. 본문은 1~200자, 최대 3줄이며 30일이 지난 메시지는 매일 삭제한다.

### 8.2 실시간 기능 구분

#### Presence

느리게 변하는 현재 상태에 사용한다.

- 온라인
- 자리 비움
- 연결된 기기
- 마지막 활동 시각

#### Broadcast

저장할 필요 없는 일시적 이벤트에 사용한다.

- 타이핑 시작
- 타이핑 갱신
- 타이핑 종료
- 이모지 반응
- 짧은 애니메이션 트리거

타이핑 이벤트는 키 입력마다 전송하지 않는다.

```text
첫 입력 → typing_start
계속 입력 중 → 2초마다 typing_keepalive
4초간 갱신 없음 → 수신 측 자동 typing_stop
전송 또는 입력 취소 → typing_stop
```

#### Postgres

메시지는 데이터베이스에 저장하고 이를 진짜 원본(source of truth)으로 삼는다. Broadcast만으로 메시지를 전달하면 잠시 연결이 끊긴 사용자가 메시지를 잃으므로 채팅 원본으로 사용하지 않는다.

### 8.3 권한과 보안

- 방 멤버만 해당 방 Presence 구독 가능
- 방 멤버만 해당 방 메시지 조회·전송 가능
- 최대 5명 제한은 서버 트랜잭션에서 검증
- 초대 코드는 DB에 평문 저장하지 않고 해시 저장
- 모든 사용자 데이터 테이블에 Supabase RLS 적용
- 방 코드를 안다는 이유만으로 기존 메시지를 조회할 수 없게 함
- 가입 후 발급된 사용자 토큰과 방 멤버십을 함께 검증
- 사용자당 최대 5개 그룹을 서버 트랜잭션에서 보장
- 같은 방에서도 닉네임 중복을 허용하고 내부 식별은 사용자 UUID로 처리
- 캐릭터 중복은 허용

### 8.4 인증

MVP 기본안은 다음과 같다.

- 최초 실행 시 기기 기반 익명 계정 생성
- 닉네임만 입력
- 인증 토큰은 OS 안전 저장소에 보관
- 온보딩 완료 로컬 상태가 있는데 저장 세션과 기존 refresh token을 모두 복원하지 못하면 새 익명 계정을 만들지 않고 복구 오류를 표시
- 추후 이메일, Google, Apple 계정 연결 지원

방 코드만 사용하는 완전 무인증 구조는 사칭과 계정 복구 문제를 만들기 때문에 사용하지 않는다.

### 8.5 배포용 백엔드 구성

- 배포 앱은 Swift `RuntimeConfiguration`에 Supabase URL과 공개 `sb_publishable_` 키를 포함해 Finder에서 바로 실행해도 실서버에 연결한다.
- `SIDEY_SUPABASE_URL`, `SIDEY_SUPABASE_PUBLISHABLE_KEY` 환경변수가 있으면 로컬 개발과 통합 테스트에서 번들 기본값을 덮어쓴다. 둘 중 하나만 설정한 불완전한 구성은 오류로 처리한다.
- `sb_secret_` 키와 legacy `service_role` JWT는 클라이언트, 앱 번들, 저장소, `.env`에 넣지 않는다.
- Hosted Realtime은 공개 채널을 허용하지 않고 `private_only`로 운영하며 Presence를 활성화한다.
- Realtime 채널 접근은 `realtime.messages` RLS가 방 멤버십을 검사하고, 메시지 원본은 계속 Postgres에 저장한다.

## 9. 메시지와 개인정보 보호

초기 Supabase 구조는 HTTPS와 데이터베이스 권한으로 보호되지만 자동으로 종단간 암호화되는 것은 아니다.

E2EE를 구현하기 전에는 다음을 주장하지 않는다.

- “종단간 암호화 메신저”
- 서버 운영자가 기술적으로 메시지를 읽을 수 없는 구조
- 민감한 대화를 위한 보안 메신저

### 수집하지 않는 정보

- 화면 내용
- 실행 중인 프로그램 목록
- 다른 프로그램에서 입력한 키
- 마우스 좌표 기록
- 파일 내용
- 음성
- 카메라

### 사용하는 시스템 정보

- 마지막 입력 이후 경과 시간
- 화면 잠금 여부
- SIDEY의 서버 연결 상태

메시지는 30일 동안 보관한 뒤 삭제한다.

## 10. 캐릭터 에셋 제작

### 10.1 스타일

전문 3D 아티스트나 대규모 Blender 작업 없이 제작할 수 있도록 단순한 스타일을 사용한다.

- cozy desktop buddy
- vinyl toy 또는 soft clay
- 살짝 치비인 humanoid
- 둥근 머리
- 명확한 팔·다리
- 벙어리장갑 같은 단순한 손
- 짧고 몸에 붙는 머리카락
- 후드티
- 무광 파스텔 재질
- 복잡한 장식 없음
- 꼬리, 날개, 긴 코트 없음

자동 리깅 실패 가능성이 높은 극단적인 SD 비율은 피한다.

### 10.2 데스크형 에셋 검증과 현재 채택본

첫 데스크형 통짜 후보는 Meshy 고해상도 원본을 Blender에서 직접 최적화해 외형과 성능만 검증했다.

```text
3,091,516 triangle 고해상도 GLB
→ Blender collapse decimation
→ 20,000 triangle
→ 재질 1개와 1024 텍스처 3장
→ USD/USDZ 변환
→ RealityKit 로더 및 SceneKit 실제 오버레이 크기 검증
```

Meshy에서 다시 생성한 50k remesh는 표면이 1,522개 loose part로 깨지고 외형과 텍스처가 심하게 열화되어 사용하지 않는다. Blender 직접 감량본은 원본 UV와 텍스처를 유지하며 약 240px 표시 크기에서 50k·100k 후보와 차이가 거의 없는 20k 후보를 기본으로 한다.

이 구형 후보는 캐릭터·의자·책상·노트북이 합쳐진 mesh 하나이고 skeleton과 shape key가 없다. 따라서 아래 항목은 정적 검증 범위가 아니었다.

- 온라인 idle, 타이핑, 수면 애니메이션
- 오프라인에서 캐릭터만 숨기기
- 노트북 열기·닫기
- 책상·의자·노트북 교체

이후 의미 단위로 분리된 캐릭터와 독립 소품을 새로 제작했으며, 구형 정적 후보를 억지로 프로덕션 에셋으로 승격하지 않았다.

동작 방향 검토에는 구형 정적 후보를 임시 분류한 5-bone 리뷰 리그를 사용했지만, 이 리그는 573개 표면 조각의 변형 파손 때문에 런타임에서 폐기했다. 현재 채택본은 다음 계약을 사용한다.

- 캐릭터 15,300 triangle, 소품 합계 6,948 triangle
- 캐릭터·의자·책상·노트북 베이스·노트북 덮개 등 5개 mesh object
- 캐릭터 19-bone skeleton과 최대 2 bone influence
- 캐릭터 텍스처 재질 1개, 소품용 단색 재질 3개
- `online_idle` 3초, `typing` 2초, `away_sleep` 3초를 30 FPS로 베이크
- 제작 GLB의 2048 텍스처 3장을 macOS USDZ에서 512로 축소
- `Zzz`는 모델에 굽지 않고 2D UI 효과로 표시
- SceneKit 카메라는 캐릭터 정면에 고정하고 책상 상판 아래를 잘라 캐릭터·노트북 중심으로 표시

### 10.3 상반신 표시, 전신 제작

프로그램에서는 상반신까지만 보여도 Meshy에서는 전신 A-pose 캐릭터를 생성한다.

```text
전신 캐릭터 생성
→ 자동 리깅
→ 애니메이션 적용
→ SceneKit 카메라로 허리 위만 표시
```

상반신만 잘린 모델은 자동 리깅이 제대로 되지 않을 가능성이 높다.

### 10.4 제작 순서

```text
Meshy Text to Image
→ 캐릭터 기준 이미지 생성
→ Image to 3D
→ Smart Topology
→ A-Pose
→ Auto Rig
→ 프리셋 애니메이션 적용
→ Text to Motion으로 타이핑 생성
→ Animated GLB 내보내기
```

### 10.5 필수 애니메이션

```text
online_idle
typing
offline_sleep
```

| 프로그램 애니메이션 | 제작 방식 |
| --- | --- |
| `online_idle` | SceneKit idle 모션 |
| `typing` | SceneKit 타이핑 모션 |
| `offline_sleep` | SceneKit 조는 모션과 SwiftUI `Zzz` 효과 |

### 10.6 타이핑 모션 프롬프트

```text
A seated character facing forward, keeping the torso mostly still,
rapidly typing with both hands on a small keyboard directly in front,
alternating subtle wrist and forearm taps,
small rhythmic head movement, no walking, no turning,
no large gestures, seamless 2-second loop.
```

타이핑 모션이 완벽하지 않으면 SceneKit과 SwiftUI에서 다음 요소로 보정한다.

- 키보드 모양의 단순한 2D/3D 도형
- 손 주변 타닥타닥 파티클
- 머리와 상체의 작은 흔들림
- 애니메이션 시작·끝 블렌딩

### 10.7 얼굴 애니메이션

MVP에서는 눈꺼풀 blendshape 같은 정교한 얼굴 애니메이션을 요구하지 않는다. 오프라인은 다음 조합으로 표현한다.

- 고개 숙임
- 어깨 내려감
- 전체 밝기 약간 감소
- 머리 위 `Zzz`
- 빨간 상태 점

작은 화면에서는 실제 눈꺼풀보다 큰 몸동작과 효과가 더 잘 보인다.

## 11. 에셋 전달 규격

제작·보관 원본은 캐릭터 하나당 모든 애니메이션이 들어 있는 GLB 하나를 우선한다. macOS 앱 번들에는 재현 가능한 변환 과정을 거친 USDZ를 넣는다.

```text
characters/
├── character_01/
│   ├── character_01_animated.glb
│   ├── thumbnail.png
│   └── manifest.txt
├── character_02/
│   ├── character_02_animated.glb
│   ├── thumbnail.png
│   └── manifest.txt
...
└── character_05/
    ├── character_05_animated.glb
    ├── thumbnail.png
    └── manifest.txt
```

하나의 GLB에 여러 애니메이션을 넣을 수 없다면 파일을 분리한다.

```text
character_01/
├── character_01_rigged.glb
├── online_idle.glb
├── typing.glb
├── offline_sleep.glb
└── thumbnail.png
```

제작 에셋 형식 우선순위는 `GLB > FBX`이고 macOS 런타임 형식은 USDZ다. OBJ와 STL은 skeleton과 animation이 없으므로 사용하지 않는다.

GLB에 텍스처가 포함되어 있으면 텍스처 파일을 별도로 받지 않아도 된다. 외부 텍스처 방식이면 관련 PNG/JPG를 모두 함께 전달받는다.

처음부터 캐릭터 5개를 제작하지 않는다. 캐릭터 한 개로 모델, 리깅, 애니메이션, USDZ 변환과 SceneKit 재생을 검증한 뒤 나머지 4개를 만든다.

## 12. 성능 방향

3D 품질보다 장시간 실행 성능을 우선한다.

- 화면에 최대 5개 캐릭터
- 캐릭터당 약 10k~20k triangles에서 시작
- 재질 1~2개
- 제작 원본은 1024 텍스처, 작은 macOS 오버레이용 USDZ 사본은 최대 512 텍스처
- 실시간 그림자 사용하지 않음
- 복잡한 조명 없음
- toon 또는 unlit 계열 재질
- 기본 30FPS
- 움직임이 없을 때 렌더링 빈도 감소
- 오버레이가 숨겨지면 애니메이션과 렌더링 일시 정지
- 잠든 상태는 마지막 프레임 고정 또는 저속 애니메이션
- 말풍선과 효과는 2D UI로 처리

한 캐릭터 vertical slice는 동일한 Godot 로컬 데모보다 10분 median CPU가 25% 이상 낮고 RSS가 더 높지 않아야 한다. 캐릭터 p95 프레임 시간은 40ms 이하, 일반 UI의 main-thread hang은 100ms 미만을 목표로 한다.

## 13. MVP에서 하지 않을 것

초기 범위에는 다음을 포함하지 않는다.

- 모바일 앱
- 웹 버전
- 공개 친구 찾기
- 불특정 다수 채팅방
- 5명 초과 그룹
- 여러 그룹 동시 표시
- 음성·영상 통화
- 이미지·파일 전송
- 화면 공유
- AI 친구·AI 챗봇
- 게임·경험치·아이템 수집
- 캐릭터 이동과 미니게임
- 사용자 임의 VRM 업로드
- 복잡한 캐릭터 편집
- 정밀 얼굴 애니메이션
- 완전한 Discord·카카오톡 대체

SIDEY의 핵심은 기능 수가 아니라 **실제 친구가 화면에 존재하는 느낌**이다.

### 0단계: 기술 검증

- SwiftUI·AppKit·SceneKit 네이티브 앱 골격과 RealityKit USDZ 로더 검증

- 가짜 버튼으로 상태 애니메이션 전환
- CPU/GPU/RAM 측정

## 16. 구현 원칙

핵심 개발 원칙은 다음 한 문장으로 요약한다.

> 캐릭터를 많이 만들기 전에, 캐릭터 한 개로 macOS 네이티브 오버레이와 상태 전환, 말풍선, Supabase 실시간 연결까지 먼저 끝낸다.

이 vertical slice가 성공하고 성능 기준을 통과한 뒤 나머지 캐릭터 4개와 꾸미기 기능을 확장한다.
