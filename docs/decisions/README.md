# 오래 남겨 둘 결정

이 디렉터리에는 현재 코드만 봐서는 이유를 알기 어렵고, 여러 구성 요소나 플랫폼의
보안·계정 체계·배포·기준 정보 경계에 오래 영향을 주는 결정만 남겨요. 현재 제품 동작을
설명하는 명세나 모든 변경을 모아 두는 일지로 쓰지 않아요.

## 어떤 결정을 남기나요?

- 되돌리기 어렵거나 여러 영역의 책임 경계를 정하는 선택을 남겨요.
- 과거 맥락을 모르면 같은 논쟁이나 실수를 반복하기 쉬운 선택을 남겨요.
- 이후 비슷한 설계를 판단할 때 다시 참고할 보안, 계정 체계, entitlement, 저장소,
  배포 결정을 남겨요.

가격·버전·상품 ID·asset hash처럼 기계가 읽을 수 있는 값, 버그 수정, 한정된 범위의
리팩터링, 일회성 출시 상태, 테스트 추가, 작업 체크리스트와 후보 검토 과정은 여기에
기록하지 않아요. 일반적인 구현 이력은 Git 커밋과 PR에 맡겨요.

## 파일 이름과 시각

새 파일 이름은 소문자 kebab-case를 사용해 `YYYYMMDDHHmm-topic.md` 형식으로 써요.
시각은 결정이 실제로 확정된 때를 Asia/Seoul (`UTC+09:00`) 기준으로 기록해요. 기존
결정을 옮길 때는 문서에 적힌 시각, 결정을 반영한 커밋, 관련 PR, merge 커밋
순서로 확인해요.

분 단위 시각을 믿을 만하게 복원할 수 없다면 임의로 `0000`, `1200`이나 문서 이동
시각을 붙이지 않아요. 이때는 `YYYYMMDD-topic.md`로 이름을 짓고 `Decided`에도 확인할
수 있는 날짜만 써요. 같은 날짜 안에서 어느 결정이 먼저였는지도 주장하지 않아요.

## 상태와 대체 관계

- `Accepted`: 현재 유효한 결정이에요.
- `Superseded`: 지금은 다른 선택으로 대체됐지만, 후속 설계를 이해하려면 이유를 계속
  보존해야 하는 결정이에요.

새 결정이 이전 결정을 대체했다면 새 문서에 `Supersedes: ./...`, 이전 문서에
`Superseded by: ./...`를 적어 서로 연결해요. 회의록, 구현 순서와 테스트 로그는 결정
본문에 넣지 않아요.

## 다른 기준 자료와의 관계

Decision 문서에는 선택 당시의 맥락, 실제로 내린 선택과 장기적인 영향만 적어요. 현재
제품 명세를 대신하지 않아요. 내용이 충돌하면 source code, project settings, catalog와
manifest처럼 기계가 읽는 자료를 먼저 확인하고, 그다음
[`../product/`](../product/overview.md)와 [`../architecture.md`](../architecture.md)의
현재 설명을 따라요. Decision은 현재 구조를 선택한 이유를 알려 주고, 일반적인 과거
이력은 Git/PR에서 찾아요.
