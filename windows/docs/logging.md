# Windows 진단 로그

진단 로그는 사용자의 대화를 기록하는 기능이 아니에요. 앱이 시작되지 않거나 오래 실행한 뒤 불안정해졌을 때, 어느 단계에서 어떤 종류의 실패가 났는지 확인하기 위한 최소한의 기록이에요.

## 로그는 정해진 위치에 세션별로 남아요

`StartupDiagnostics`는 다음 폴더에 로그를 만들어요.

```text
%LOCALAPPDATA%\SIDEY\Logs
```

파일 이름은 다음 형식이에요.

```text
SIDEY.<밑줄로 구분한 버전>.<yyyyMMdd>.<HHmmss>.log
```

예를 들어 버전 `1.2.1`을 2026년 9월 12일 03:04:05 UTC에 시작했다면 `SIDEY.1_2_1.20260912.030405.log`가 돼요. 모든 시각은 UTC로 기록해요. 사용자의 지역 설정에 따라 로그 해석이 달라지지 않게 하기 위해서예요.

치명적인 시작 실패가 나면 오류 대화 상자에 이 로그 경로를 보여 줘요.

## 단계, 복구 가능한 실패, 치명적 실패를 구분해요

현재 진단 API는 일반적인 여섯 단계 로그 레벨을 제공하지 않아요. 실제로 필요한 세 가지 형태만 기록해요.

- `Stage(name)`은 시작과 종료 과정이 어디까지 진행됐는지 기록해요.
- `NonFatal(stage, exception)`은 앱이 계속 실행할 수 있는 실패를 기록해요.
- `Fatal(stage, exception, showDialog)`은 정상 실행을 계속할 수 없는 실패를 기록하고 필요하면 대화 상자를 열어요.

이렇게 나누는 이유는 심각도를 꾸미려는 게 아니에요. 로그를 읽는 사람이 “앱이 멈췄는가, 복구해서 계속 실행했는가”를 바로 판단할 수 있어요.

세션 시작에는 앱 버전, 빌드 버전, OS 버전, OS·프로세스 아키텍처, .NET 런타임, 프로세서 수를 남겨요. 시작 완료와 정상 종료 표식도 남겨요. 직전 로그 끝에 정상 종료 표식이 없으면 다음 시작에서 `previous-session-end result=unclean`을 기록해요.

## 예외 메시지 전체를 기록하지 않아요

예외 메시지에는 서버 응답, 경로, 토큰처럼 예상하지 못한 개인정보가 섞일 수 있어요. 그래서 `StartupDiagnostics`는 메시지 전체 대신 다음처럼 문제를 분류하는 정보만 남겨요.

- 예외 형식과 HRESULT
- 최대 여덟 단계의 내부 예외 형식
- 소스 경로를 지운 호출 스택
- HTTP 상태 코드
- DNS, 소켓, TLS, 시간 초과 분류
- Win32 네이티브 오류 코드
- 파일 오류에서는 전체 경로가 아닌 파일 이름

같은 실패가 반복되면 `repeat` 횟수를 붙여요. 반복 여부를 알기 위해 민감한 요청 내용까지 기록할 필요가 없기 때문이에요.

## 개인정보를 로그에 넣지 않아요

다음 값은 성공·실패 여부와 관계없이 기록하지 않아요.

- 메시지 본문, 입력 중인 글자, 닉네임, 이메일
- 액세스 토큰, 갱신 토큰, 자격 증명, 초대 코드
- 원본 사용자·방·메시지 UUID
- 키 입력, 마우스 좌표, 화면 내용, 활성 앱 목록
- 파일 내용과 전체 사용자 경로
- 사용자 이름과 컴퓨터 이름

식별자가 필요해 보여도 먼저 그 값 없이 같은 문제를 구분할 수 있는 단계명, 개수, 상태 분류를 사용해요. 임의로 해시한 식별자도 여러 로그를 연결할 수 있으므로 기본적으로 남기지 않아요.

```csharp
StartupDiagnostics.Stage("realtime-connect-start");

try
{
    await session.ConnectAsync(cancellationToken);
}
catch (HttpRequestException exception)
{
    StartupDiagnostics.NonFatal("realtime-connect", exception);
}
```

이 기록만으로 연결 시작 여부와 HTTP 실패 종류를 알 수 있어요. 방 ID나 서버 응답 본문은 필요하지 않아요.

## 로그가 앱을 방해하지 않게 해요

진단 기록 자체의 실패 때문에 시작이나 종료가 실패해서는 안 돼요. 로그 쓰기와 정리는 최선 노력으로 실행해요.

- 파일 하나는 최대 4 MiB예요. 한도에 도달하면 표식을 한 번 남기고 이후 기록을 버려요.
- 로그는 최대 30일 동안 보관해요.
- 폴더에는 최대 100개, 합계 32 MiB까지만 보관해요.
- 정리는 시작할 때와 실행 중 6시간마다 시도해요.

앱이 실행 중이면 1분마다 working set, private bytes, 관리 힙 크기, 핸들 수, GDI·USER 객체 수를 기록해요. 이 값은 장시간 실행에서 자원이 계속 늘어나는지 찾기 위한 지표예요. 사용자의 화면이나 작업 내용은 포함하지 않아요.

로그를 추가하거나 바꿀 때는 실제 기록 한 줄을 검토해 금지된 값이 들어갈 경로가 없는지 확인해요. 디버깅 절차는 [`debugging.md`](debugging.md)를 따라요.
