# Windows character feedback

The feature uses scene-local stun state, the existing native pixel renderer, WinUI pending selection indicators, and Windows animation preferences. Sound files are deployed once under `Assets/Impacts/<throwable ID>/<throwable ID>.wav`; `Assets/Impacts/manifest.json` records relative paths and approved WAV hashes. Each throwable has its own folder, and the old `Assets/Audio/Impacts` tree is rejected by deployment verification.

Settings contain a single row with a volume label, speaker mute button, current percentage and a 0–100% slider. There is no toggle switch, description paragraph, sound picker or preview button. The slider explicitly uses the WinUI DefaultSliderStyle for its round thumb. Changing the slider to zero mutes effects; moving it above zero unmutes them. Manual mute preserves the chosen volume, and turning effects on from zero restores the last positive volume from this app session (100% initially). The slider remains usable while muted. Its default soft-ball feedback plays once on pointer release or key release after a value change, never during dragging or after an idle/save timer. Loading, reverting settings, cancellation and leaving the settings page do not play feedback. Toggle and volume changes are persisted together after a short debounce and flushed on normal exit.

## Performance boundaries

- All eight PCM WAV files and four XAudio2.9 source voices are prepared on a dedicated MTA worker. The shared output graph stays running while sound is enabled and the desktop is unlocked; it is not reset for each short effect or slider release. Playback submits immutable PCM without file reads, decoding or output creation. Neither the UI thread nor the native renderer waits for preparation or device operations.
- Incoming playback requests are capped at 64 queued requests, four voices and 80ms between starts. Canceling the most recent playback scope also clears its start restriction so the next slider release is not suppressed by a canceled sample. Requests more than 500ms old are dropped. Muting, closing a preview, switching rooms and shutting down invalidate old requests. Default output changes invalidate requests and rebuild the output graph on the worker.
- Throw and hit images are cached before native rendering starts. The 36 stun effect frames are computed once. Rendering uses cached pixels rather than decoding PNGs or allocating new effect frames for each hit.
- The store preview still uses its existing UI timer; it stops the timer and playback when animation effects are disabled. Window and media callbacks ignore expired presentation/playback generations.
- Volume changes apply to SIDEY's XAudio2 mastering voice. Zero volume invalidates requests, stops active voices and suspends the engine. Scope cancellation stops only active source voices; it does not reset the output device. Native voices are destroyed before freeing shared PCM memory.

## Startup overlay

After loading preferences and before starting authentication, a completed-onboarding user with a visible overlay and cached nickname gets their cached character with the gray reconnecting indicator. `CachedStartupWorld` is presentation-only: its single local identity and null room ID are never persisted or sent to the backend. Startup interactions cannot publish actions. An initial network failure leaves this scene visible. Hidden overlays, missing/invalid cached nicknames and incomplete onboarding do not create a placeholder.

The first server snapshot replaces the cached identity and members in the same native session. Snapshot presence uses the gray reconnecting indicator until the active room transport is connected, including while message reconciliation is pending. Existing reconnecting indicators are preserved, and the current user remains visible even when offline peers are filtered. A server-confirmed missing profile/group clears the cached presentation. Internal Debug character validation continues using its own scene.

`SIDEY_OVERLAY_STARTUP_SMOKE=1`, together with the normal isolated startup harness, verifies that a native frame is presented without a backend, the first server snapshot stays in the gray connecting state, and transport connection promotes members to online without replacing the native session. The synthetic smoke uses no authentication or server calls during these checks. Core 151 tests, Windows platform 295 tests, Release publish and this native startup smoke passed. Test build: `build/windows/character-feedback-startup-overlay/SIDEY.exe`.

## First-hit, slider and stun corrections

The first test build could submit a short WinMM buffer successfully without the user hearing it. Inspection found no long leading silence: soft-ball energy is concentrated in roughly the first 90ms, while the duck remains audible through roughly 300ms. All eight approved files peak near -14dBFS. Output startup clipping is a candidate, not an acoustically proven diagnosis. The XAudio2 graph replaces per-voice WinMM output/reset calls; approved WAV bytes and levels are unchanged.

`SoundVolumeSlider` hooks the template's horizontal and vertical `Thumb.DragCompleted`, plus track pointer release and adjustment-key release. Completion is queued once after the control's final value update; duplicate completion events consume the same pending feedback only once. Cancellation, focus loss and unloading discard pending feedback. Runtime checks verify the native slider template actually supplied the Thumb hooks; automated tests do not inject physical mouse drags.

Stun stars have a seven-pixel silhouette with a contrasting outline and a wider vertical orbit. `CharacterNameplateLayout` places labels at a fixed distance of 22 logical pixels from the foot on all four edges; character silhouette, animation frame and stun state never move that anchor. Text determines label width. Both the native overlay and preview share this rule, reserving the full head/effect area even before stun. Effects render after all nameplates, including neighboring labels. The preview reserves enough cached rectangles for two simultaneous effects. Its smoke checks compare expected effect colors against the composed preview, including a deliberately overlapping label to verify draw order.

## Realtime startup latency correction

The 12:14 UTC user log shows a snapshot at +2.2s, a receive failure during the initial channel join, an eight-second scheduled recovery, and active-room connection at +13.4s. A read-only topic-join probe using the original transport reproduced a Windows SocketException ConnectionAborted / native 10053. This establishes a socket-level interruption in that probe, not which OS/network component caused it. Microsoft documents the code in [Winsock errors](https://learn.microsoft.com/en-us/windows/win32/winsock/windows-sockets-error-codes-2). The probe reads an existing session and authorized room metadata; it never refreshes credentials, tracks presence, publishes messages or sends transient events.

The transport now fails pending replies immediately when its receive loop loses the socket, logs a sanitized failure category/code, and handles transient initial subscription errors through background recovery so activity monitoring and remaining initialization can continue. The first reconnect waits 350ms, followed by 8/16/30-second backoff on consecutive failures. Independent channel joins are sent concurrently, and only successful join acknowledgements enter the connected-topic map. Cancellation while waiting for the send gate also removes pending reply registrations.

Local loopback WebSocket regression tests verify both joins arrive before either reply, out-of-order replies, no premature connected status, immediate release of interrupted joins, and recovery within three seconds after an injected first-connection loss. Core 151 and Windows platform 302 tests passed. Release publish and framework/approved-audio checks passed. Read-only live joins with the new published assemblies completed in 1.952, 1.814 and 1.815 seconds (socket connect plus both subscriptions). Sequential baseline successful runs took 1.876–1.931 seconds, so this environment did not demonstrate a material speedup from parallel joins. These are transport measurements after room lookup, not end-to-end application startup measurements. The improvement demonstrated by the regression test is removal of the five-second pending wait and initial eight-second recovery delay. Test build: `build/windows/character-feedback-fast-connect/SIDEY.exe`.

## Wi-Fi loss and paused recovery

The 12:25 UTC user run reached active-room transport at +3.06 seconds. Later Wi-Fi loss produced no `realtime-network-unavailable` event: the fallback heartbeat noticed 19.872 seconds of receive silence, and DNS failures continued through the 350ms/8s/16s/30s schedule. The existing `NetworkInterface.GetIsNetworkAvailable` checks for an up adapter, not Internet access ([Microsoft contract](https://learn.microsoft.com/en-us/dotnet/api/system.net.networkinformation.networkinterface.getisnetworkavailable)).

`SystemNetworkAvailabilityMonitor` now reads the preferred Windows Internet profile's connectivity level and subscribes to `NetworkStatusChanged`, `NetworkAddressChanged`, and adapter availability events. None/LocalAccess/null means unavailable; InternetAccess and ConstrainedInternetAccess allow attempts. If the OS profile query itself fails, a routed up adapter is a fallback. No profile names, SSIDs, addresses or packet contents are logged, and there is no periodic connectivity query. Microsoft's [recommended profile/event flow](https://learn.microsoft.com/en-us/uwp/api/windows.networking.connectivity.connectionprofile.getnetworkconnectivitylevel) is used.

An offline event immediately marks the transport disconnected, aborts its socket, cancels scheduled recovery and waits for a new Internet availability event. Recovery starts after 350ms on restoration. If an Internet path exists but the service remains unavailable, automatic attempts continue with bounded backoff, eventually one attempt per 30 seconds. Ongoing snapshot/message reconciliation and its retry wait are canceled on transport loss so they cannot block delivery of the disconnected state. Cancellation also tolerates disposal racing a previous recovery's completion.

Windows platform 309 tests passed, including real loopback WebSocket tests for immediate disconnected status, interrupted reconciliation, no new socket while offline, and automatic reconnection after availability returns; focused network tests passed again after the cancellation race guard. Release publish, approved audio/framework guards and isolated app/overlay startup smoke passed. Physical Wi-Fi was not switched by the agent, so OS notification timing remains a user-device check. Test build: `build/windows/character-feedback-network-aware/SIDEY.exe`.

## Resilient connection recovery

This follow-up supersedes the preceding LocalAccess exclusion and 30-second retry cap. Windows connectivity is a hint: None/no profile pauses connection attempts, while LocalAccess and constrained access allow an actual service attempt. Microsoft explicitly recommends attempting the service with LocalAccess or higher in its [NetworkInformation guidance](https://learn.microsoft.com/en-us/uwp/api/windows.networking.connectivity.networkinformation). Profile/address changes can interrupt backoff even when availability remains true; a healthy connection is retained for ordinary network hints. The existing native window receives PBT_APMRESUMEAUTOMATIC and requests a fresh socket and acknowledged subscriptions after resume.

Retry delays are initially 350ms, then nominally 8/16/30/60/120/240/300 seconds, with ±20% jitter after the first attempt and an absolute 300-second cap. Recovery hints bypass the long delay and coalesce within one second. Explicit path loss cancels scheduled recovery, reconciliation, and an initial handshake that has not installed its socket yet. Restoration starts after 350ms. No polling of network profiles, Wi-Fi activation, or credential replacement was added.

Missing sessions and HTTP 400/401/403 failures pause automatic retries. Channel authentication/authorization rejection permits one reconnect with a fresh session read, then pauses if rejected again; unknown errors and server/rate-limit failures remain retryable. Error classification follows the named categories in [Supabase's Realtime channel implementation](https://github.com/supabase/realtime/blob/master/lib/realtime_web/channels/realtime_channel.ex), without retaining raw reasons. Network hints/resume do not clear this pause. The sidebar connection status is an accessible retry button while disconnected. Manual retry after an access rejection refreshes the account/group snapshot first. Failed initialization can also be retried without concurrent duplicate initialization or replacing an existing backend/session.
