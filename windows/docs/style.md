# Windows C# 코드 스타일

코드 스타일의 목적은 모든 사람이 같은 취향을 갖게 하는 게 아니에요. 코드를 읽을 때 형식보다 동작에 집중하게 만드는 게 목적이에요. 자동으로 판별할 수 있는 규칙은 도구에 맡기고, 리뷰에서는 이름과 책임, 실패 처리처럼 맥락을 살펴야 하는 부분에 집중해요.

이 문서는 Microsoft의 [C# 식별자 명명 규칙](https://learn.microsoft.com/ko-kr/dotnet/csharp/fundamentals/coding-style/identifier-names)과 [일반적인 C# 코드 규칙](https://learn.microsoft.com/ko-kr/dotnet/csharp/fundamentals/coding-style/coding-conventions)을 기본으로 삼아요. 특정 게임 엔진이나 프레임워크에서만 통하는 관례는 그대로 가져오지 않아요. 저장소의 코드와 도구에 맞는 규칙만 사용해요.

## 먼저 도구의 결과를 따라요

`windows/.editorconfig`가 C#과 XAML의 기본 형식을 정해요. 개인 IDE 설정과 다를 때는 저장소 설정이 우선해요.

- C#과 XAML은 UTF-8, CRLF, 공백 네 칸을 사용해요.
- 파일 범위 네임스페이스와 Allman 중괄호를 사용해요.
- `using`은 네임스페이스 밖에 두고 `System` 항목을 먼저 정렬해요.
- 인터페이스는 `I`, 인스턴스 필드는 `_`, 정적 필드는 `s_`로 시작해요.
- 네임스페이스는 폴더 구조와 맞춰요.
- `CA2012`와 `CA2025` 위반은 빌드 오류로 처리해요.

스타일을 눈으로 맞추기보다 다음 명령으로 확인해요.

```powershell
dotnet restore windows/SIDEY.Windows.slnx
dotnet format windows/SIDEY.Windows.slnx --verify-no-changes --no-restore
dotnet build windows/SIDEY.Windows.slnx --configuration Release --no-restore
dotnet test windows/SIDEY.Windows.slnx --configuration Release --no-restore --no-build
```

자동 검사를 통과했다고 이름과 구조까지 읽기 쉬운 것은 아니에요. 도구가 판단하지 못하는 부분은 아래 원칙으로 살펴봐요.

## 이름으로 역할을 예상할 수 있어야 해요

예를 들어 `Handle()`만 봐서는 무엇을 언제 처리하는지 알 수 없어요. `RetryConnectionAsync()`는 연결을 다시 시도하고 비동기로 끝난다는 사실을 이름만으로 보여 줘요. 이렇게 동작을 예측할 수 있으면 호출부를 읽을 때 구현 파일을 열어 보는 횟수가 줄어요.

이름의 대소문자와 접두사는 다음처럼 맞춰요.

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 네임스페이스, 형식, 메서드, 속성, 이벤트 | `PascalCase` | `Sidey.Overlay.Rendering`, `ConnectionState` |
| 인터페이스 | `I` + `PascalCase` | `IHistoryCoordinator` |
| 지역 변수, 매개변수 | `camelCase` | `retryCount`, `cancellationToken` |
| 인스턴스 필드 | `_camelCase` | `_connectionState` |
| 정적 필드 | `s_camelCase` | `s_defaultTimeout` |
| 스레드 정적 필드 | `t_camelCase` | `t_currentContext` |
| 상수 | `PascalCase` | `MaximumRoomCount` |
| 제네릭 형식 매개변수 | `T` 또는 `T` + 역할 | `T`, `TMessage` |

위치 기반 `record`의 매개변수는 공개 속성이 되므로 `PascalCase`를 사용해요. 일반 생성자와 메서드의 매개변수는 `camelCase`를 사용해요.

```csharp
public sealed record MessageSnapshot(string Text, DateTimeOffset SentAt);

public sealed class MessageStore
{
    private readonly string _connectionString;

    public MessageStore(string connectionString)
    {
        _connectionString = connectionString;
    }
}
```

이름에는 역할에 필요한 정보만 넣어요.

- 비동기 메서드는 실제로 비동기 작업을 반환할 때 `Async`로 끝내요.
- 단위나 좌표계가 중요한 값은 `timeoutMs`, `logicalPosition`, `screenPixels`처럼 이름에 드러내요.
- `Attribute`를 상속한 형식은 `Attribute`로 끝내요.
- 일반 enum은 단수형을 사용하고, `[Flags]` enum은 조합을 나타내도록 복수형을 사용해요.
- 불리언 이름은 참일 때 무엇을 뜻하는지 긍정형으로 표현해요. `Is`, `Has`, `Can`은 뜻이 자연스러울 때 사용하되 접두사를 기계적으로 강제하지 않아요.
- 이벤트는 이미 일어난 상태 변화를 나타내는 이름을 사용해요. 이벤트를 발생시키는 메서드는 .NET 관례에 따라 `OnConnectionChanged()`처럼 이름을 붙일 수 있지만, 이벤트 자체에 `On`을 붙이지 않아요.
- 앱 전체를 가리키는 이름보다 기능을 드러내는 이름을 사용해요. `IApplicationCoordinator`보다 `IHistoryCoordinator`처럼 범위를 알 수 있는 이름이 나아요.

약어가 팀 밖의 독자에게도 명확하지 않다면 풀어 써요. 다만 HTTP, DPI, Win32처럼 널리 쓰이며 문서에서 이미 설명한 용어는 억지로 늘이지 않아요. 한 글자 이름은 짧은 반복문의 인덱스나 수식처럼 범위와 의미가 바로 보일 때만 사용해요.

C#에서는 키워드 앞에 `@`를 붙이거나 유니코드 문자를 식별자로 사용할 수 있어요. 하지만 쓸 수 있다는 이유만으로 읽기 어려운 이름을 만들지는 않아요. 키워드를 피할 수 있는 명확한 영어 이름을 사용하고, 컴파일러가 예약한 형태로 오해할 수 있는 이중 밑줄 `__`도 사용하지 않아요.

## `var`는 타입이 바로 보일 때 사용해요

오른쪽 식만 보고 타입을 알 수 있다면 `var`가 중복을 줄여 줘요.

```csharp
var coordinator = new AppCoordinator(...);
```

반대로 반환 타입이 동작을 이해하는 데 중요하거나 식만으로 알기 어렵다면 타입을 써요.

```csharp
CoordinatorState state = await stateStore.LoadAsync(cancellationToken);
```

짧게 쓰는 것보다 중요한 정보를 가까이 두는지가 기준이에요. `string`, `int`, `bool`처럼 C# 키워드가 있는 형식은 `String`, `Int32`, `Boolean` 대신 키워드를 사용해요.

## 최신 문법은 뜻이 더 잘 보일 때 사용해요

새 문법이라는 이유만으로 기존 코드를 바꾸지는 않아요. 코드가 짧아지면서 의도도 분명해질 때 사용해요.

- 문자열을 조합할 때는 `+`를 이어 붙이기보다 문자열 보간을 사용해요.
- 반복문에서 문자열을 계속 만들 때는 불필요한 할당을 줄이도록 `StringBuilder`를 검토해요.
- 따옴표와 줄바꿈이 많은 문자열은 원시 문자열 리터럴이 더 읽기 쉬운지 살펴봐요.
- 형식이 분명한 컬렉션은 컬렉션 식을 사용할 수 있어요.
- `using` 선언으로 자원의 수명이 현재 범위와 자연스럽게 일치하면 선언문을 사용해요.
- LINQ가 변환 의도를 더 잘 보여 주면 사용해요. 렌더 루프처럼 자주 실행되는 경로에서는 할당과 실행 시간을 측정한 뒤 선택해요.

`&&`와 `||`는 왼쪽 조건에 따라 오른쪽 식을 실행하지 않을 수 있어요. 이 단락 평가가 null 접근이나 비용이 큰 호출을 막는 조건이라면 평가 순서가 이름과 구조에서 드러나게 작성해요.

## 중괄호와 줄바꿈으로 실행 범위를 보여 줘요

중괄호는 실행 범위를 눈으로 확인하게 해요. 지금은 한 줄뿐인 조건문도 다음 수정에서 문장이 추가될 수 있으므로 생략하지 않아요.

- 여는 중괄호는 새 줄에 둬요.
- `if`, `else`, 반복문에는 본문이 한 줄이어도 중괄호를 사용해요.
- 한 줄에는 문장 하나와 지역 변수 선언 하나만 둬요.
- 연산자와 쉼표 주변의 공백은 `.editorconfig`에 맡겨요.
- 공백으로 여러 줄의 토큰을 세로 정렬하지 않아요. 이름이나 형식이 바뀔 때 불필요한 수정이 늘어나요.

고정된 줄 길이로 코드를 자르지는 않아요. 한 줄에 정보가 너무 많아 흐름을 따라가기 어렵다면 식을 의미 있는 이름으로 나누거나 호출 구조를 단순하게 만들어요.

## 함께 바뀌는 코드를 함께 둬요

응집도는 같은 이유로 바뀌는 코드를 가까이 두는 정도예요. 한 클래스가 연결 재시도와 픽셀 렌더링을 함께 맡으면 어느 한쪽을 바꿀 때 다른 쪽의 상태와 수명까지 확인해야 해요. 서로 다른 이유로 바뀌는 책임은 분리해요.

- 한 파일에는 독립적인 주 형식 하나를 둬요.
- 메서드는 한 가지 결과를 만들도록 구성해요.
- 잘못된 입력과 종료 조건은 guard clause로 먼저 처리해요.
- 매개변수가 많아 호출 의미를 기억하기 어렵다면 관련 값을 하나의 형식으로 묶거나 책임을 나눌 수 있는지 살펴봐요.
- 비슷한 오버로드가 늘어날수록 호출자가 차이를 외워야 해요. 선택 사항이 실제로 같은 동작인지 확인하고, 서로 다른 동작이라면 이름과 책임을 나눠요.
- 상태를 바꾸는 메서드는 이름과 반환값에서 그 사실을 예상할 수 있게 해요. 조회처럼 보이는 메서드에 숨은 부작용을 넣지 않아요.
- 임의의 줄 수를 기준으로 형식이나 메서드를 나누지 않아요. 함께 바뀌는 이유가 다른지가 기준이에요.

주석은 코드만으로 알 수 없는 이유를 기록해요. Win32 제약, 개인정보 보호 경계, 성능을 위해 택한 트레이드오프는 좋은 주석이에요. `count++` 옆에 “수를 증가시킨다”라고 쓰는 주석은 코드와 같은 말만 반복해요.

공개 API도 이름과 형식만으로 계약이 충분히 드러나면 설명을 되풀이하는 XML 주석을 달지 않아요. 사용 조건, 예외, 소유권처럼 호출자가 코드만 보고 알 수 없는 계약이 있을 때 문서화해요.

## 예외를 숨기지 않아요

처리할 수 있는 가장 구체적인 예외를 잡아요. 복구할 수 없다면 상위 경계로 전달해요. 다시 던질 때는 원래 호출 스택을 보존하도록 `throw;`를 사용해요.

넓은 `catch`는 다음처럼 실패가 프로세스 밖으로 새면 안 되는 경계에서만 사용해요.

- 프로세스 시작과 종료
- UI 명령과 네이티브 콜백
- 렌더 루프
- 진단 기록 자체의 실패

이 경계에서도 실패를 조용히 없애지 않아요. 개인정보를 넣지 않은 진단을 남기거나 사용자가 할 수 있는 복구 동작으로 바꿔요.

## 비동기 작업과 자원의 주인을 드러내요

I/O는 끝까지 `await`해요. `.Result`, `.Wait()`, `.GetAwaiter().GetResult()`로 막으면 UI 스레드가 멈추거나 교착 상태가 생길 수 있어요.

장시간 작업을 시작한 객체는 작업을 보관하고, 취소하고, 예외를 관찰하고, 종료할 때 완료를 기다려야 해요. 타이머, 소켓, 네이티브 핸들, 취소 토큰 소스도 만든 쪽의 해제 책임이 코드에서 보여야 해요.

`ValueTask`는 동기 완료가 실제로 잦고 한 번만 기다린다는 계약이 분명할 때 사용해요. 단순히 `Task`보다 빠를 것 같다는 이유로 바꾸지 않아요.

## GlobalUsings를 작게 유지해요

전역 using은 프로젝트 전반에서 반복되는 네임스페이스를 줄이는 도구예요. 특정 기능만 쓰는 네임스페이스까지 넣으면 각 파일이 어디에 의존하는지 찾기 어려워져요.

새 항목을 추가할 때는 다음을 확인해요.

1. 프로젝트의 여러 파일에서 반복되는가?
2. 이름 충돌 없이 형식의 출처를 예상할 수 있는가?
3. 금지된 프로젝트 의존을 감추지 않는가?

셋 중 하나라도 아니라면 해당 파일에 지역 using을 둬요.

## 사용자 문구는 코드에 넣지 않아요

사용자에게 보이는 문구는 `src/Sidey.App/Langs/*.json`에 키로 관리하고 `I18n.Get()` 또는 `I18n.Format()`으로 읽어요. 코드에 한국어나 영어를 직접 쓰면 언어를 바꿀 때 빠지기 쉽고 번역 카탈로그의 동등성 검사도 받을 수 없어요.

로그의 개인정보 규칙은 [`logging.md`](logging.md), 번역 규칙은 [`localization.md`](localization.md), 계층 규칙은 [`architecture.md`](architecture.md)를 따라요.
