# 한국어 기술 문서 문체

한국어 문서는 [Frontend Fundamentals의 코드 품질 문서](https://frontend-fundamentals.com/code-quality/code/)처럼 전문 용어를 피하지 않으면서도, 독자가 처음 만난 개념을 그 자리에서 이해할 수 있게 설명해요.

## 해요체로 설명해요

본문은 비격식체의 해요체로 써요. `합니다`, `됩니다` 같은 격식체와 `한다`, `된다` 같은 문어체를 섞지 않아요. 독자에게 명령을 이어 붙이기보다 `확인해요`, `사용하지 않아요`처럼 같은 높이에서 설명해요.

코드 식별자, 제품명, API 이름과 명령은 원형을 유지해요. `ValueTask`, `Win32`, `GlobalUsings`처럼 개발자가 검색하거나 코드에서 찾아야 하는 이름을 어색한 한국어로 바꾸지 않아요.

## 전문 용어를 가까이에서 풀어 줘요

전문 용어를 쉬운 말로 바꾸기만 하면 정확한 검색어를 잃어요. 용어는 그대로 쓰되 처음 나오는 문장에서 뜻을 설명하고, 이어지는 문장에서 왜 중요한지 보여 줘요.

`응집도를 높여요`라고만 쓰면 독자는 응집도가 무엇인지 따로 찾아야 해요. 다음처럼 뜻과 결과를 붙이면 문맥을 놓치지 않아요.

> 응집도는 같은 이유로 바뀌는 코드를 가까이 두는 정도예요. 연결 재시도와 픽셀 렌더링이 한 클래스에 있으면 어느 한쪽을 바꿀 때 다른 쪽의 상태와 수명까지 확인해야 해요.

## 추상적인 효과를 구체적으로 바꿔요

`유지보수성이 향상돼요`처럼 결과를 뭉뚱그리지 않아요. `호출부를 읽을 때 구현 파일을 열어 보는 횟수가 줄어요`처럼 누가 무엇을 덜 확인하게 되는지 써요.

소유권이나 책임이 중요할 때는 주어를 생략하지 않아요. `해제되어야 해요`보다 `핸들을 만든 객체가 해제해요`가 책임을 더 분명하게 보여 줘요. 피동문이 자연스러운 경우까지 억지로 바꾸지는 않지만, 행위자를 감추는 피동 표현은 피하는 편이 좋아요.

## 한국어 문장의 리듬을 살려요

- `또한`, `따라서`, `이를 통해` 같은 접속사를 문단마다 반복하지 않아요.
- 비슷한 길이의 문장과 불릿을 같은 박자로 이어 붙이지 않아요.
- 명사만 이어 붙인 번역투보다 누가 무엇을 하는지 보이는 문장을 사용해요.
- 괄호 안에 예외와 보충 설명을 쌓지 않아요. 중요한 내용은 문장으로 꺼내요.
- 영어 병기와 인용 부호, 굵은 글씨를 강조 수단으로 남용하지 않아요.

짧은 문장만 쓰는 것도 목표가 아니에요. 한 문장에는 하나의 중심 생각을 두되, 원인과 결과를 함께 읽어야 이해하기 쉽다면 자연스럽게 이어 써요.

## 설명을 목록으로 잘게 부수지 않아요

비교 대상, 선택지, 확인 절차처럼 항목의 경계가 중요할 때는 표와 목록이 도움이 돼요. 이유와 맥락을 설명하는 문장까지 모두 불릿으로 만들면 글의 흐름이 끊겨요. 독자가 앞 문장과 다음 문장을 이어 읽어야 하는 내용은 문단으로 써요.

## 마지막에 말투를 한 번 맞춰요

초안을 다 쓴 뒤에는 다음 항목만 확인해요.

- 해요체가 아닌 종결어미가 섞이지 않았는가?
- 전문 용어의 뜻과 필요한 이유가 가까이 있는가?
- 추상적인 장점만 말하고 구체적인 결과를 빠뜨리지 않았는가?
- 접속사, 문장 길이, 불릿 구조가 기계적으로 반복되지 않는가?
- 자연스럽게 다듬는 과정에서 식별자와 기술적 의미를 바꾸지 않았는가?
